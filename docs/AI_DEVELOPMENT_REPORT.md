# Отчет о работе с ИИ при разработке исследовательского Telegram агента

Дата: 29 сентября 2026 года. Этот отчет составлен от лица заказчика проекта на основании фактической текущей сессии. Он описывает использование ИИ для разработки самого бота. Автоматические научные исследования, которые бот выполняет, учитываются отдельно в его журналах.

## Моя задача и исходные материалы

Я передал Codex техническое задание в файле «Финальный проект_ИИ-агент.pdf» из папки `DL_2nd_semester`. Я запросил три результата: запускаемый код, человекочитаемую документацию и полный отчет о применении ИИ. Дополнительно я задал Telegram-интерфейс, discovery по приблизительной области, итеративное согласование реализации и использование DeepSeek. Ключи Telegram и DeepSeek я предоставил в исходном сообщении; здесь они удалены.

В этой сессии зафиксированы исходный пользовательский промпт разработки и последующий запрос статуса. Архитектурные и технические решения принимал Codex при выполнении исходного запроса. Я не приписываю себе отдельные промпты, которых не было в переписке.

### Мой исходный промпт

```text
привет! прочитай реализацию финальный проект_ии агент. пдф в папке, пожалуйста создай следующие артефакты - 1.код агента, готовый для запуска, с возможностью написать ему в бота телеграм [TELEGRAM_BOT_TOKEN УДАЛЕН] добавь возможность discovery - то есть я пишу примерную область, агент предлагает темы работ и после утверждения задает вопросы по реализации итеративно в телеграм, после этого выполняет саму работу в жестких требованиях по ГОСТу 2.полную документацию бота в стиле readme, человекочитаемую 3.полный отчет по работе с ИИ с моей стороны - какие промпты были написаны, какие субагенты вызваны и какие скиллы/мсп задействованы для разработки самого ИИ агента. В качестве LLM используй deepseek с ключом [DEEPSEEK_API_KEY УДАЛЕН].
```

Также среда передала список доступных плагинов и контекст рабочей папки. Они не являются отдельными моими содержательными запросами на проектирование.

### Мой запрос статуса

```text
посмотри статус сейчас
```

По этому запросу Codex проверил процесс Telegram-бота, сохраненную стадию исследования и последние события журнала. На момент проверки пользовательское исследование выполнялось; контрольный запуск разработки был прерван до экспорта. Помощник сообщил это без заявления о готовых DOCX/PDF и продолжил незавершенную проверку.

## Что сделал ИИ помощник

Codex обнаружил и прочитал все три страницы PDF. Из него были извлечены требования к архитектуре Orchestrator/Retriever/Analyzer/Reporter/Validator, LangChain или GigaChain, LangGraph, LCEL, Plan-and-Execute, памяти, Semantic Scholar, arXiv, RAG, научной достоверности, DOCX/PDF и минимуму 15 источников.

Далее помощник сверил официальные документы DeepSeek, Telegram, arXiv, Semantic Scholar и LangGraph, а также текст ГОСТ 7.32-2017 с поправками. Он создал Python-проект с раздельными модулями, схемами Pydantic, Telegram-диалогом, SQLite-памятью и графом исследования. Выбран допустимый в задании LangChain. Для LLM используются DeepSeek API и OpenAI-совместимый клиент: это не использование OpenAI как модели бота.

Помощник записал предоставленные мной ключи в локальный `.env` с правами `0600`, исключил его из исходников для распространения и добавил `.dockerignore`. Онлайн-проверка Telegram подтвердила имя `diplom_gost_bot`. DeepSeek `/models` вернул `deepseek-flash` и `deepseek-v4-pro`; конфигурация была исправлена со старого `deepseek-chat` на фактически доступный `deepseek-flash`. Значения ключей в отчет не включены.

Для вывода документов создан детерминированный DOCX-шаблон. PDF конвертируется из того же DOCX через LibreOffice: этот выбор сохраняет верстку и заменяет неподходящую для прямой конвертации библиотеку ReportLab. Содержание пересчитывается по реальным страницам. Формат DOCX выбран из разрешенных заданием вариантов DOCX/ODT; ODT не реализован. Embedding-модель FastEmbed работает локально и заменяет пример text-embedding-3-large из PDF, не требуя второго LLM-ключа.

## Субагенты при разработке

В этой сессии **субагенты Codex не вызывались: количество 0**. Все чтение, проектирование, кодирование, проверка и подготовка документов выполнены основным агентом текущей задачи. Инструменты `collaboration.spawn_agent`, `create_thread`, `send_message_to_thread` и другие механизмы делегирования не применялись. Имена вымышленных субагентов и несуществующие промпты делегирования в отчет не добавлены.

Внутри разработанного программного продукта есть роли `discovery`, `requirements`, `planner`, `analyzer`, `critic`, `repair`, `abstract`. Это отдельные последовательные вызовы одной модели DeepSeek с разными промптами, а не вызванные при разработке субагенты Codex. Критик не является независимой моделью: его систематические ошибки могут совпадать с ошибками автора текста.

## Навыки, MCP и инструменты среды

| Инструмент или навык | Фактическое использование при разработке |
|---|---|
| `pdf:pdf` | Чтение задания, извлечение текста pypdf, рендер страницы PDF и проверка страниц |
| `documents:documents` | Построение и визуальная проверка DOCX-шаблона, использование `render_docx.py`, проверка темы и стилей Word |
| `mcp__codex_app__load_workspace_dependencies` | Получение путей к Python/Node и поставленным зависимостям для работы с документами |
| `functions.exec` | Оркестрация вызовов инструментов и обработка результатов |
| `exec_command`, `write_stdin`, `wait` | Чтение файлов, запуск Python, uv, pytest, Ruff, программного экспорта и сетевых проверок |
| `apply_patch` | Создание и исправление исходников, конфигурации и документации |
| `web__run` | Проверка актуальных официальных API и текста стандарта; отдельные страницы DeepSeek не загрузились, поэтому доступность модели проверена реальным API |
| `view_image` | Просмотр отрендеренного задания и страниц тестового DOCX/PDF |
| `mcp__codex_app__open_in_codex` | Отправлен запрос открытия итогового README в рабочей панели; инструмент вернул queued |

MCP в этой разработке использован как интерфейс инструментов Codex. Сам бот не является MCP-сервером и не требует подключения MCP для работы. Он вызывает Telegram, DeepSeek, Semantic Scholar, arXiv и источник модели Hugging Face напрямую через SDK/HTTP.

Не применялись навыки генерации изображений, презентаций, Google Drive, Google Docs, Google Sheets, создания сайтов, Raindrop и Work Pets. Плагины из списка рекомендаций не устанавливались. Нет оснований утверждать, что Slack, Notion, Figma или другие перечисленные сервисы участвовали в проекте. LangSmith предусмотрен конфигурацией, но без отдельного пользовательского ключа при разработке не включался.

## Промпты, написанные Codex для готового бота

Исходные тексты хранятся в `research_agent/prompts.py`. Ниже указан их смысл; точные версии включены в [приложение PROMPTS.md](PROMPTS.md), автоматически извлеченное из исходника.

| Промпт | Когда используется | Ограничения |
|---|---|---|
| `SYSTEM` | Каждый вызов LLM | Русский ответ, JSON по схеме, запрет выдумывать источники/эксперименты, документы считаются данными |
| `DISCOVERY` | После приблизительной области | 4 выполнимые темы, вопрос, метод и доступность, без заявления об уже выполненном поиске |
| `FOLLOWUP` | После обязательных ответов | Один новый вопрос, отсутствие повторов, максимум 3 уточнения, согласование доступной реализации |
| `PLAN` | Начало LangGraph | Цель, вопросы, гипотезы, английские запросы, критерии включения и ограничения |
| `SECTION` | Каждый раздел отчета | Тип утверждения, реальные id и точные подтверждающие фрагменты, отсутствие вымышленных цифр |
| `REVIEW` | Self-check раздела | Проверка поддержки утверждений контекстом, числовых оснований и различия обзора/эксперимента |
| `ABSTRACT` | После проверки разделов | Реферат и 5–15 ключевых слов без новых фактов |

Исправление использует исходный `SECTION` с дополнительными данными `draft` и `corrections`, содержащими черновик и конкретные обнаруженные нарушения. При ошибке JSON LCEL-промпт получает краткое сообщение валидации и повторяет вызов один раз. Это программно создаваемые уточнения, а не мои дополнительные сообщения Codex.

После реальной проверки цикл исправления расширен до двух доработок каждого раздела. Модель получает полный проблемный `draft`, список `corrections` и сводку реального размера корпуса. Промпт требует сохранять условия сравнения, не переносить вывод одной модели на все семейство и отдельно маркировать интерпретации. Проверки не ослаблялись ради успешного результата.

Помимо текстовых промптов, в LLM передается структурированный JSON: область, выбранная тема, ответы и уточнения, JSON Schema ожидаемого результата, план, найденные фрагменты, обязательные id источников, реально вычисленные метрики CSV и замечания критика. Секреты из `.env` в исследовательский контекст не передаются.

## Проверки, ошибки и исправления

Проведены проверки доступа к Telegram и DeepSeek, реальный платный discovery с четырьмя темами, поиск arXiv с 35 результатами по проверочному запросу, загрузка multilingual embedding-модели и поиск FAISS. Semantic Scholar без отдельного ключа вернул ограничение запросов; это зафиксировано как недоступность данного провайдера при smoke-тесте, а не как успешно полученные статьи.

Автоматические тесты проверяют дубликаты по названию/DOI/arXiv ID, фиктивные цитаты, неизвестные ссылки, недостаточное цитирование, реальные вычисления CSV, авторизацию владельца, восстановление диалога, FAISS, библиографию без придуманных страниц, скрытие секретов, обработку API и пустого поиска, контроль DOCX, полный граф на тестовых данных, восстановление после сбоя и отказ критика. Telegram-сценарий discovery и согласования ТЗ проверен с имитацией API-вызовов, а не с личными сообщениями пользователя.

После прерывания контрольного запуска добавлено сохранение проверенных разделов по SHA-256 отпечатку задания, источников, RAG-контекста, схем, модели и промптов. Два дополнительных теста проверяют повторное использование завершенного раздела после сбоя и обязательную повторную генерацию при изменении промпта. Для продолжения старого контрольного журнала пять ранее принятых ответов и вердиктов восстановлены только при точном совпадении записанных входов и актуальных промптов; текущая машинная проверка выполнена заново. Фиктивные научные ответы при таком восстановлении не создавались.

В первой проверке графа тестовый LLM-клиент был создан без тестового ключа; после добавления фиктивного offline-ключа тесты прошли. Это ошибка тестового окружения, не подмена реального ключа. При проверке PDF выяснилось, что pypdf извлекает footer раньше основного текста: проверка последних строк ошибочно отклоняла существующие номера. Валидатор исправлен на координатную проверку в нижней части листа. Отдельно настроено физическое центрирование номера при асимметричных полях.

Визуальная проверка обнаружила наследуемую синюю линию стандартного стиля Word Title и шрифты темы у заголовков. Код очищает границы и theme-font атрибуты и задает Times New Roman для всех письменностей. Тестовый документ помечен как синтетический и не является научной работой или моим финальным исследованием.

В следующем полном запуске валидатор ошибочно распознал доверительный интервал вида `[0,546; 0,799]` как вставленную библиографическую ссылку. Шаблон распознавания исправлен, добавлен отдельный регрессионный тест. Также обнаружено, что критик иногда помещает успешные проверки и неблокирующие замечания в список ошибок: схема дополнена отдельным `notes`, а блокировка связывается с машинными нарушениями или явным `accepted=false`. Научные блокеры продолжают запрещать экспорт. В контекст добавлено фактическое описание автоматического отбора, чтобы агент не приписывал себе ручной систематический скрининг.

При обновлении работающего бота повторный SIGTERM прервал завершение пользовательского исследования после проверки шести разделов и формирования реферата. Помощник признал ошибку. Из сохраненного графа и журнала восстановлены проверенные разделы и реальный реферат, после чего продолжена проверка и экспорт. Итоговый пользовательский отчет содержит 35 страниц и 20 источников; в Telegram доставлены DOCX, PDF и три JSON-файла контроля/источников/подтверждений. Скрипт перезапуска исправлен: запрос остановки сохраняется для конкретного PID, повторный запуск скрипта ожидает завершения и не посылает второй сигнал. Это фактическая ошибка сопровождения и ее исправление, а не заявленный успешный перезапуск без проверки.

Фактические финальные результаты запусков находятся в [VALIDATION.md](VALIDATION.md). Проверочный полный цикл с реальными источниками хранит журнал в `data/runs/acceptance/audit.jsonl` и результаты в `output/acceptance/`; эти файлы предназначены для проверки программы.

## Что я получил

Я получил исходники исследовательского Telegram-агента, конфигурацию и lock-файл зависимостей, команды запуска, Dockerfile/compose, пример ТЗ, тесты, README, матрицу соответствия и настоящий отчет о разработке с приложением промптов. Мой дальнейший рабочий процесс: открыть бота, выбрать область, утвердить тему и ТЗ, проверить полученный отчет перед использованием.

Полного ручного научного рецензирования каждого будущего отчета, сертификации ГОСТ, обучения моделей и разворачивания круглосуточного сервера в эту сессию не включено. Содержание работы и формальное оформление остаются моей ответственностью как автора. Код предоставляет проверяемые свидетельства и конкретные ограничения, чтобы я мог выполнить такую проверку.
